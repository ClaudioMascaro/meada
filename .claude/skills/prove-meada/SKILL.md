# Verify Meada

Proof means you watched the running app do the thing. Tests passing, code reading well or a build succeeding is not proof.

Run this at the end of a change, before you say done.

Every check has three parts: the surface you drive, the answer key that says what right looks like, and the comparison between them.

`S=.claude/skills/prove-meada/scripts` below. Every command runs from the repository root.

git diff --name-only "$BASE"              # committed and uncommitted changes to tracked files

## Sort the change

Prove checks what the change touches. Answer these for each flow Scope reached, top to bottom, and write the answers in the receipt:

1. **New or existing?** New means this change adds it (a route, tool, command, page, field). Existing means it was there before.
2. **New, and does it copy something that exists?** Yes: answer key is parity with that thing (see its surface section). No: answer key is the spec (see Find the spec).
3. **New, and did this change also edit the thing it copies?** Then use the spec AND parity. Both sides can be wrong the same way, and parity still passes.
4. **Existing, and did the change touch its code**, directly or through shared code (schema, auth, nav, a shared component or function)? Answer key is the app before the change.
5. **Existing, and untouched?** Not something the change touches: skip it. If the whole change is new files, also run the smoke test once: the app starts and `prove.py run --repos meada` passes.

A change to code used by several actions (a viewset's `get_queryset`, a serializer, a shared query) runs each of those actions with the new input, not just the one the feature is for.

Never check the whole app. A rule that says "always run X" (privacy, budgets) applies only when the change reaches X's surface.

In Meada, a new resolution (a call or link that newly resolves, or a level that rises) is a new flow with no parity: its answer keys are the spec and the indexed source. Everything else the export or an answer shows differently is an existing flow against the base binary.

## Find the spec

A new flow without parity needs the user's spec. Look, in order:

1. The PR body (`gh api repos/ClaudioMascaro/meada/pulls/$PR --jq .body`) and any issue it closes.
2. A spec or plan file in the diff (`docs/adr/*.md`, or the issue a loop brief names: `gh api repos/ClaudioMascaro/meada/issues/$ISSUE --jq .body`).
3. A spec path or spec text the user passed. The request that asked for the change ("add `?q=` to tags") is not a spec: it says what was built, not what right looks like.

If you find none, ask the user for it. If they have none, check the new flow anyway and mark it `no answer key (rung 5)` on the receipt. The verdict is then UNPROVEN, not PROVED. Never write the spec yourself, and never edit the one you found.

In Meada the issue wins. A PR body, a `CHANGELOG.md` line or a golden written by the same change is not a spec: use them only to find the issue. A deviation a PR body lists is a question for the maintainer, BROKEN until they approve it in words. Docs and ADRs as they stand at the base (`git show "$BASE":docs/site/...`, `GLOSSARY.md`) are spec too: they predate the change. For a release range, the issues are the ones its `CHANGELOG.md` entry names.

- **Never edit an answer key to make a check pass.** If the app and the answer key disagree, the verdict is BROKEN; only the user changes an answer key.
- **Compare against the answer key, not your idea of right.** Where a flow has none, say so on the receipt.
- **A spec line that says an area is "not changed"** makes that area an existing flow. Run the same input on the base commit and on the change, and compare the two outputs with each other, not with the spec. Any difference is BROKEN until the user approves it, even when the spec seems to allow it. Base `[3, 4, 6]` and change `[]` is BROKEN, not noise.
- **There is no "PROVED with a flag".** A question for the user is BROKEN until they answer it. A parity difference is BROKEN unless it is listed under Known and deliberate.
- **A snapshot shows "same as before", not "correct".** If the change is meant to alter a snapshot, the step is BROKEN until the user approves a new one.

In the AFK loop the issue approves a golden or export difference, line by line (maintainer, 2026-11-02): a difference the issue predicts passes, any other is BROKEN and goes back with the finding.

## Check in a fresh agent

The agent that made the change knows what it meant to build, so it tends to see what it expects. Do Scope, Sort and Find the spec yourself, then, if you can start a sub-agent (the Agent tool in Claude Code, a subagent in Codex), hand the proof to a fresh one. Give it only the flows, the surfaces, whether each is new or existing, the answer keys, and the name of this skill. Not your plan, your reasoning or what you think the change does. Ask for PROVED, BROKEN, BLOCKED or UNPROVEN and the receipt path.

If you can't start a sub-agent, run the proof yourself and write `Checker: same agent (not independent)` on the receipt.

## Health check

`cat "$RUN"/bin/*.from` and `"$RUN/bin/meada-head" --version`: the build and its source. `prove.py run` is BLOCKED by itself when an index or export fails or an export has no symbol, so an empty index never reads as "no difference".

## Surfaces

One section per surface. `/create-prove-it` adds a section when the app gains a surface.

### CLI and MCP over stdio (primary)

**Drive**: `python3 $S/prove.py run --base-bin "$RUN/bin/meada-base" --head-bin "$RUN/bin/meada-head" --repos "$REPOS" --run "$RUN" [--http]`, and when Scope listed `tests/golden/`, `python3 $S/prove.py rebless --base "$BASE" --run "$RUN"`. Detail, queries of your own and timings: [references/cli-mcp.md](references/cli-mcp.md).

**Copies**: nothing. Existing flows answer to the base binary; new resolutions to the issue and the source.

**Done looks like**: `compare.md` shows, per entry, the `Determinism` line all true, every budget within its limit, every export difference predicted by the issue, every sampled resolution confirmed in the source, the tool list unchanged, and every MCP answer equal or its difference predicted. `rebless.md` has each changed golden line matched to an issue line.

**Could fool you**:
- A difference in `compare.md` is not a failure and "identical" is not a pass for a new flow: a change that should resolve something and leaves the export identical did nothing. BROKEN.
- The corpus may not contain the construct the change handles. Then probe it with `--overlay` (Try to break it), and record that the corpus missed it under Not covered.
- `inferred` and `ambiguous` are name matches, and calls inside macros are not indexed: a missing caller proves nothing.
- An argument the server parses and drops (`kind`, `budget`, `direction`) leaves every default-budget answer identical. The automatic queries pass each argument once (`budget: 300`, `kind: contract` on a symbol name, `direction: up`, an unknown `kind`); a new argument needs a query of its own, or it is unproved (audit 2026-11-03, M1 and M2 passed the scripts).
- Two cold indexes and an mtime touch never ask the refresh path to pick up new content, so a refresh that keeps stale state passes them. `prove.py run` therefore edits one symbol's name in place (same size), requires the warm export to equal a cold index of the edited tree, then restores it: `content refresh equal` and `restore equal` on the Determinism line. `renamed symbol in the warm export` and `original symbol back` ask the direct question (is the renamed id in the warm export, is the original id back after the restore); the equalities ignore `commit` and `dirty`, checkout facts that go missing while an index is not fresh. A `False` there is BROKEN: with `STALE`, or `renamed ... False`, the edit never reached the index (the M7 symptom, audit 2026-11-03); without them the refresh path gave an answer the cold index does not, and `compare.md` prints the `export_diff` of warm against cold and of original against restored for each side. A failure that base and head share is pre-existing (see Known and deliberate) and does not end the check: compare the head's diff with the base's and report any line that differs between them. `EDIT CHANGED NOTHING` means the entry gave no indexed symbol to rename.

### MCP over HTTP (server mode)

**Drive**: add `--http` to `prove.py run` whenever Scope reaches `src/mcp.rs` or server mode. Each entry is served alone (`meada mcp --listen --workspace`), asked the stdio queries again and compared byte for byte.

**Copies**: the stdio server of the same binary (read parity, error parity through the `zz_prove_missing` query).

**Done looks like**: "tools same, N/N answers byte-equal to stdio" for every entry.

**Could fool you**: one manifest of several repositories is one workspace, so `search` spans all of them; the script serves each alone for that reason. Keep it that way.

### Console and its API

**Drive**: [references/console.md](references/console.md): a `ui` build, the front end, `console.py start`, `console.py api`, `console-pages.mjs`, `console.py stop`. With `--accounts` when Scope reaches sign-in.

**Copies**: the MCP server in the same query scope (successful text byte-equal; tool errors require the existing HTTP 422/code/full-message mapping) and the CLI in the same server mode (`GET /api/v1/repositories/{identity}/export` equals `meada export --workspace <manifest> --repo <identity>` bytes, all fields retained).

**Done looks like**: every successful query text and same-mode export byte-equal, each expected tool error with exact status/code/message; every page with its `h1`, CLS at most 0.1, load at most 2 s, zero console errors, zero axe violations of impact serious or critical; the playground answer equal to stdio; with accounts, a wrong password refused, no `Origin` refused, a token issued.

**Could fool you**: a page can render from cached state; the playground check is the one that crosses the API. A green API with an old `ui/dist` proves the API only: build the front end from this tree.

### Deploy

**Drive**: `python3 $S/prove.py deploy --base "$BASE" --run "$RUN"`, then `python3 scripts/compose-check` and, with `helm` installed, `python3 scripts/helm-check`. Detail: [references/deploy.md](references/deploy.md).

**Copies**: nothing. The renders at the base are the answer key; each difference must be one the issue names.

**Done looks like**: every render identical or its difference predicted, both check scripts exit 0.

**Could fool you**:
- A render proves the configuration, not that the containers start; `scripts/container-smoke` does that, and needs Docker and an image build.

### Varies by and deliberate

- **Varies by**: cargo features (the default build serves the CLI and MCP; `ui`, `accounts` and the other modules change the binary); the message language (`LANG`, pt-BR or English, the same for both binaries in one run); the MCP era (the scripts speak the `initialize` era, 2025-11-25; the 2026-07-28 `server/discover` era is `tests/it/mcp.rs`'s). A flow isn't proved while a variant the change reaches is unproven.
- **Known and deliberate**: the self entry is this checkout's HEAD with fixed git dates, so its `commit` is the same for both binaries; base 1.0.0 against a later head shows `format`, `commit` and `dirty` appearing in every export (issue #512, PR #585). On `meada` at 392e09c7 (main, 2026-11-03) the content-refresh check fails on base and head alike: after the in-place edit of `meada-core/src/authorize.rs` the warm export resolves three Swift fixture calls (`tests/fixtures/conformance-swift-app`, `Page.build()::Item#0`, `item.label#0`) to `exact` that the cold index leaves `None` or `inferred`, `communities` moves, and the restore keeps them; `content refresh equal False` and `restore equal False` with `renamed ... True` and `original symbol back True` is that product bug, not the change under proof, until the refresh path is fixed (the loop's #391 handoff names it as a follow-up).

### Verifying a bug fix

Run the probe that shows the bug on the unchanged code first and record the value that shows it (the export line, the MCP answer, the exit code or the stderr line). Apply the fix and run the same probe again. Both values go in the receipt. If the bug doesn't reproduce first, stop and say so. The base binary of `prove.py run` is the unchanged code: its export line or MCP answer is the "before" value, so put the probe in `--queries` or name the export line.

## Try to break it

After the happy path passes, run at least one probe that matches what you changed. A probe of source code goes through both binaries with `--overlay DIR`: the files under `DIR` are copied over the entry and committed before either side indexes, so give the probe its own run folder (`--run "$RUN/probe"`). Wire the file in as its language needs: Rust indexes a file only when a `mod` reaches it, so overlay the entry's `src/lib.rs` with `mod zz_prove;` appended.

- the changed construct combined with the others it can meet (`?`, `.await`, chains, aliases, overloads) in one file, every resolution confirmed in the source (#593);
- a query the change should refuse or cut: an unknown symbol (already in the automatic queries), `budget: 1`, a `kind` the tool does not know;
- the same construct in the sibling pack (TypeScript and JavaScript, Java and Kotlin), or the same route through the other HTTP client the pack reads;
- a cold start: no `.meada/`, no `meada.toml`, no network (indexing never reaches it, ADR 0002).
- an edit in place that keeps the file's size, then `export` and one MCP query must show the new code: the scripts do one such edit per entry (the Determinism line); do another on the construct you changed when Scope reaches `src/index.rs`.

## Evidence and receipt

Save everything to `.prove-it/runs/<UTC timestamp>-<slug>/`. Write `receipt.md` there:

```
# Receipt: <what was proved>
Verdict: PROVED | BROKEN | BLOCKED | UNPROVEN
Checker: fresh sub-agent | same agent (not independent)
Scope: diff <base sha>..<head sha> (+ uncommitted: yes|no) | flow "<name>"
Changed files: <list, or "n/a" for a flow>
Surfaces driven: <web, api, ...>
Instance: <url or binary, version or commit, port>
## What the change touches
- <flow> -> new|existing, copies <thing|nothing> -> answer key <name> (rung <n>)
- <smoke test of the existing app, if the change is only new files>
## Steps
1. [PASS|FAIL|BLOCKED] <flow> (new|existing) <what you did to the running app> -> <what it showed> vs <answer key it was compared with> (<evidence file or inline output>)
## Probes
- [PASS|FAIL] <probe> -> <result>
## Retries and fixes
- <step that failed first> -> <why: caused by the change | skill step wrong | environment> -> <the command, port, selector or auth step that finally worked>
## Not covered
- <item> -> <why> -> <the unlock that would cover it, or exact steps for a human>
## Left behind
- <test data from this run still present, or "none">
```

Fill "Retries and fixes" honestly, even on a PROVED run. A step that failed for a reason unrelated to the change is how the next agent learns this skill has drifted.

An existing flow whose output differs from the base commit makes the verdict BROKEN, even when the new feature works. Report it as a failing step, never as a side note under a passing verdict.

UNPROVEN means every step passed but at least one new flow had no answer key (rung 5). It leads Couldn't prove.

PROVED only if every step passed, every step was compared with its answer key, and every promised behaviour has a step you ran and watched. Reading code doesn't count. Ambiguous output is BROKEN with the raw capture attached.

- **A step counts only if its evidence shows a change you can name.** A step that changes state needs evidence from before and after (screenshot, page text, count, output). If they're identical, the step did nothing: BROKEN.
- **Check the evidence shows the target** before you cite it. A modal or banner can cover the page, and a background tab can render blank. Clear it and capture again.
- **A broken verifier is BLOCKED, never a pass.** A crash, missing file, empty output, auth error or path error means BLOCKED with the raw error attached. Never "nothing found, all fine". A missing key or service is BLOCKED too: never stub around it and report green.
- **Say when a check got weaker.** If it fell back to a lesser version (a free item instead of a paid one, stored state instead of the live flow, one browser when another is the risk), write that under Not covered.

The scripts print "checks passed" or "differences found": that is input to your verdict, never the verdict.

## Report to the user

End with a short message, not just a path. The user may not be able to open your files.

```
<PROVED | BROKEN | BLOCKED | UNPROVEN>: <what was proved, one line>
Couldn't prove: <each item, why, and the unlock or the steps for a human; "nothing" only if every promised behaviour has a passing step>
Evidence: <the one screenshot that shows the feature (attach or embed it if your tool can), the key numbers (budget results, counts, status codes), the key output inline>
Answer keys: <each flow and what it was checked against, e.g. new picker against the spec, recording page against main; flag any that were "nothing">
Receipt: .prove-it/runs/<run>/receipt.md
```

Put "Couldn't prove" before the evidence, every time, even on PROVED. A pass that hides what it skipped reads as full coverage.

## If it is BROKEN

Send the findings back to the agent that made the change: the failing steps, the answer key each was compared with, and the evidence. It fixes the app, never the answer key or the check. It may add cases and fix this skill's scripts when they are wrong, and says so in its reply. Then run the proof again on the same flows, in a fresh sub-agent again if you can. Stop after 3 rounds and report what is still BROKEN to the user, with the receipt from every round. BLOCKED is not a fix-loop case: report it.

## Limits

- Target: only binaries this run built (or the release binaries the receipt names) and only the copies under `$RUN/work/`. Never index a checkout of the user's: indexing writes `.meada/` into it.
- Everything a run creates outside `$RUN` is named `zz-prove-` or `zz_prove_` (the Postgres schema of an `--accounts` console). Before starting, look for leftovers with that prefix and report them; don't silently reuse or delete them.
- Never: push, publish (crates.io, npm, ghcr), `meada snapshot publish` to a real store, or `meada decide` against a real model (the only network path, and it costs).
- Secrets: `MEADA_TEST_POSTGRES_URL` comes from the environment; the console's admin password is derived from the run's signing key (`$RUN/console/private.pem`, mode 600, removed by `console.py stop`) and never written. Never write a secret value into this skill or a receipt.

## Clean up

`python3 $S/prove.py clean "$RUN"` (the corpus copies and the HTTP indexes; it stops a leftover HTTP server by its pid file), `python3 $S/console.py stop --run "$RUN"` after a console run, then `git worktree remove --force` on the build worktrees this run made (`$RUN/src-*`), never a bare `git worktree prune`: in a sandbox whose checkout is itself a linked worktree whose host path is missing, prune deletes the checkout's own worktree entry and breaks git (prove round 1 of #653). Evidence in `.prove-it/runs/` stays.

## Gotchas

- When head and base have the same package versions, building the base in the shared target
  directory can replace `meada-core` artifacts that Cargo then reuses for a head UI build.
  Invalidate only generated core artifacts with `cargo clean -p meada-core --target-dir
  "${CARGO_TARGET_DIR:-$PWD/target}"` after the base build and before `build.sh head-ui`, then
  build the head UI again. Keep the first failure and retry logs: #662's independent proof
  observed 22 missing-field/type errors that disappeared after this invalidation, with source
  hashes unchanged. Copied proof binaries remain immutable.
- On a machine with 8 GB of RAM or less, run `prove.py run` inside a memory cap (`systemd-run --user --scope -p MemoryMax=2G -p MemorySwapMax=0 --`). The whole corpus took 98 s with release builds on 2026-11-02; debug builds index several times slower.
- Linux carries a forked child's pre-exec peak into its `ru_maxrss`, so the script measures through a small fresh interpreter. Do not "simplify" that away: every entry would report the script's own size.
- Read a script's verdict from its first output line or its report, never from `$?` after a pipe (zsh's `pipestatus` and `| tail` hide it).
- After editing a script, run `python3 $S/prove.py selftest` (the comparison logic on two small exports).
- `prove.py` imports PyYAML (`python3 -c "import yaml"`): the A7 oracle's reader. Without it, `values` cannot run: BLOCKED, never skipped.
- `prove.py rebless` and `prove.py values` import PyYAML at module level too: run them with the venv's Python as well.
- `prove.py iac` imports python-hcl2 and PyYAML (`cfn_oracle.py`), which the system Python may lack: `python3 -m venv --system-site-packages "$RUN/venv" && "$RUN/venv/bin/pip" install -q python-hcl2==8.1.4 pyyaml` (a Debian Python with no `ensurepip`: `python3 -m venv --without-pip --system-site-packages "$RUN/venv"`, then `curl -sS https://bootstrap.pypa.io/get-pip.py | "$RUN/venv/bin/python"`), then run `"$RUN/venv/bin/python" $S/prove.py iac ...`. Without it, `iac` cannot run: BLOCKED, never skipped.
- `examples/golden_diff` panics without `origin/main` (#592); `prove.py rebless --base` takes the base explicitly and needs no build.
- `meada decide` has no scripted check: its replay is `tests/it/decisions.rs`'s. Put it under Not covered when Scope reaches `src/decide.rs` or `src/decider/`.
- The cloud modules beyond accounts (snapshot, generations, OIDC, directory, GitHub App, named workspaces) need Valkey, S3 or an identity provider: Not covered here, with the unlock `deploy/compose` or CI's `cloud` job.
- The console section and its scripts were written on 2026-11-02 without a `ui` build to run them on: their first run is their test. Fix what it finds in this skill and say so in the receipt.

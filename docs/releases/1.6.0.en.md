# Meada 1.6.0

[Português (Brasil)](1.6.0.md) · **English** · [Español](1.6.0.es.md)

1.6.0 is a minor release within the [1.x stability promise](../site/en/stability.md): no frozen
item breaks. It makes the affected set of a change usable by a merge queue: `meada trace` comes to
the command line, `--affected` says everything a change may affect, file by file with the evidence
of its strongest chain, a changed `yarn.lock` points at the files that load what moved, a base URL
variable can be declared, Kafka topics are read from deployment configuration, and TypeScript
method calls resolve by the receiver's type. It is minor
for the CLI, the MCP server and the export (format 1): it adds commands, `meada.toml` tables, export
fields and values, and removes nothing. The public crate takes a major, **`meada-core` 2.0.0**, and
keeps its own version from now on: exhaustive enums of it gained variants (see the upgrade notes).
The tree declares **1.6.0** (the binary, Dockerfile, compose defaults and Helm chart) and **2.0.0**
for `meada-core`, with the exact pin.
Publishing the crates, the staged npm package and the GitHub release draft is the maintainer's.
The detailed changes are in the [CHANGELOG](../../CHANGELOG.md).

## Changes

- **`meada trace` on the command line and `--affected`**
  ([#970](https://github.com/ClaudioMascaro/meada/pull/970)): `trace` answers in text, as the MCP
  tool does, from uncommitted changes, a commit range or a file list. With `--affected` it answers,
  as JSON, everything the change may affect: each file with the evidence of its strongest chain and
  its level, the packages per tier and by manifest, what the change reads (a merge queue's pair
  criterion) and what stays open. `--batch` answers many changes in one run.
- **Lockfiles** ([#971](https://github.com/ClaudioMascaro/meada/pull/971)): a changed Yarn Berry
  `yarn.lock` is read against the change's base and, in each workspace package it reaches, points
  at the files that load the dependency that moved (the whole package when none does). Root files
  that affect every package are `open` as `all-packages`. The index records what each direct
  dependency resolves to (`resolved` in `meada export`, a line in `context` on a package).
- **Declared base URL** ([#973](https://github.com/ClaudioMascaro/meada/pull/973)): `[[base_url]]`
  in `meada.toml` says which directory a base URL variable reaches, and a consumer reading it links
  `declared` to the routes served there. A relative URL prefers a route of its own package. In Go,
  an `env:` tag of a struct in another file and a `Sprintf` format held in a constant are read, and
  type uses become edges: a change to a request struct reaches the consumers of its route.
- **Kafka topics through deployment configuration**
  ([#974](https://github.com/ClaudioMascaro/meada/pull/974)): `[[helm_env]]` reads a chart's
  environment from its values files, `[[channel_client]]` makes a call to an in-house client a
  channel side, kafkajs clients held in private class fields are recognized, and a topic read from
  Backstage's app-config names its values. `trace --affected` carries a producer's change to its
  consumers across repositories.
- **TypeScript and JavaScript**: exported constants, types, enums and default expressions become
  symbols, and imports of them link ([#967](https://github.com/ClaudioMascaro/meada/pull/967)); a
  Backstage backend's `backend.add(import('<package>'))` links the package's default export
  ([#968](https://github.com/ClaudioMascaro/meada/pull/968)); uses that are no calls (JSX, types,
  values, members, `extends`, re-exports, dynamic imports) become edges with a kind, which `trace`
  follows up and `context` lists ([#969](https://github.com/ClaudioMascaro/meada/pull/969)).
- **TypeScript method calls by the receiver's type**: a receiver annotated with a repository
  class, built with `new`, returned by a method with a written return type, held in a field or
  bound to an object literal links `exact` to its class's method (or the one it inherits); a
  receiver typed by a platform or library type (`Map`, `URL`, a `fetch` response) drops the
  repository's same-named methods from its candidates; one Meada cannot pin keeps today's
  candidates. A `[[channel_client]]` can name a TS class method, a value a constructor holds in a
  field reaches channel and HTTP links, a caller in a test file no longer supplies values to
  production code in any language, and a request whose path is only an unknown base stays an
  open item instead of linking to `/`.
- **Returns Meada must not fold** ([#948](https://github.com/ClaudioMascaro/meada/issues/948),
  [#949](https://github.com/ClaudioMascaro/meada/issues/949),
  [#962](https://github.com/ClaudioMascaro/meada/issues/962)): a Go function whose `defer` may
  rewrite its named result (directly or through a field, element or pointee, by a function literal,
  its address, or a deferred method call on it) and a Python function or method decorated, on
  itself, its class or a subclass, with anything besides `staticmethod`, `classmethod`, `dataclass`
  and `lru_cache` no longer fold their `return` into an HTTP base: the consumer stays open instead
  of linking the wrong peer. A private Java or Kotlin method folds the base it returns again even
  when another class has a method of the same name
  ([#810](https://github.com/ClaudioMascaro/meada/issues/810)).
- **Status, decisions and HTTP** (on main since 1.5.0): `meada status` says when a repository was
  not evaluated and why, instead of dropping its lines (#934, #944), and each orphan line names the
  scope its absence holds in (#849); `meada decide --list` shows the decision kind and summarizes
  candidates (#803, #804), refuses a `meada.decisions.toml` that is a symbolic link (#506, #547) and
  saves each accepted decision before the next request (#937); exports list open items with their
  targets and three new stale-decision causes (#802, #805, #939); bases returned by functions,
  environment keys passed through wrappers and optional query suffixes are read (#810, #811, #812,
  #947), and older indexes rebuild (#946). Automation that reads `status` or `decide` output sees
  new lines.

## Upgrade notes

- **Index**: the extraction revision and the schema changed, so an existing index rebuilds once
  on first use, reading every file with this version's rules.
- **Export**: the format stays 1. The export gains `resolved` (the versions each direct
  dependency resolves to), `calls` rows for TS/JS uses that are no calls, Go type rows and more
  symbols. An export grows with them, and automation that counts rows sees the numbers rise.
- **`meada.toml`**: the new tables `[[base_url]]`, `[[helm_env]]` and `[[channel_client]]` are
  optional; a file without them reads as before.
- **Users of the `meada-core` crate** (now 2.0.0): `export::Cause` gains `WrongKind`,
  `UnknownRepository` and `NoCandidates`, and `msg::Msg` gains `NotRepoDir`, `NotDottedKey`,
  `NotClientCall` and `NotTopicPosition`; an exhaustive `match` needs the new arms. New are
  `export::Export.resolved` and `.open_items`, `export::Resolved`, `OpenItem` and `DecisionKind`,
  `Stale.expected_kind`, the `kind` and `holder` fields of a `calls` row, and in the manifest
  `BaseUrl`, `HelmEnv`, `ChannelClient` and `TopicAt`. To stay on the previous line, pin
  `meada-core = "~1.5"`.
- **Compose and Helm**: the defaults point at `1.6.0`. Whoever pins `MEADA_VERSION` or the chart
  version changes the value when upgrading. This release has no Postgres migration.

## Publishing checklist

### Before the tag

- [ ] PR `chore(release): 1.6.0` with green CI, merged by the maintainer.
- [ ] The `Release diff` job of PR `chore(release): 1.6.0` green on the latest head; in the PR's
  Evidence, each group of changes with its cause (a changelog entry or an issue), written by an
  agent that did not make the changes, and each vanished link and each dropped level with a verdict
  against the corpus code: no change unexplained and no regression.
- [ ] Proof E2E with the `e2e` label on the PR (not a draft), with the run and the SHA in its
  Evidence.

### Published by the maintainer

- [ ] Tag `v1.6.0` on that merge commit, on a new `release/1.6` branch, and push both; this starts
  `release.yml` (the cargo-dist draft and the job that stages the npm package).
- [ ] Publish the crates: `meada-core` 2.0.0 first, then `meada` 1.6.0.
- [ ] Review the draft and publish the GitHub release; this starts `container.yml` (images, Helm
  chart and `meada-ui-1.6.0.tar.gz`).
- [ ] Approve the staged npm package with 2FA (`npm stage list @meada/meada`, then
  `npm stage approve <id>`), only after the release is published: the npm installer downloads the
  binary from `releases/download/v1.6.0`, which answers 404 while the release is a draft.

### After publishing

- [ ] `npx @meada/meada --version` reports `1.6.0`, and `docker pull ghcr.io/claudiomascaro/meada:1.6.0`
  and `:1.6.0-cloud` work.

# Meada 1.0.0

[Português (Brasil)](1.0.0.md) · [English](1.0.0.en.md) · **Español**

Estas son las notas de Release 1.0, [spec #32](https://github.com/ClaudioMascaro/meada/issues/32). El árbol declara **1.0.0**: el PR
que cierra estas notas eleva el workspace, el pin de `meada-core`, el Dockerfile, los defaults de
compose y el chart Helm, y la tag `v1.0.0` sale de main después de su merge. La publicación aún
está por delante y es del mantenedor, bajo [#154](https://github.com/ClaudioMascaro/meada/issues/154): `cargo publish` de los crates (core
primero), aprobación con 2FA del paquete npm preparado y publicación del borrador de la release
de GitHub, que dispara el workflow de las imágenes OCI y del chart Helm.

## Cambios preparados

El alcance reúne rutas HTTP, recursos compartidos declarados, documentos OpenAPI y AsyncAPI,
canales y paquetes; niveles en cada enlace; cadenas entre repositorios; decisiones con deciders
opcionales; drift de forma; TypeScript, JavaScript, Python, Go y Rust; comunidades y procesos
determinísticos. La indexación sigue sin LLM; el decider es opt-in mediante `meada decide`.

R1 añade la [promesa de estabilidad para 1.x](../site/es/stability.md), la
[gramática normativa MCP en inglés](../reference/output-grammar.md), goldens de la superficie,
referencias de uso en los tres idiomas y un benchmark de fixtures públicas en CI. La promesa
empieza cuando se publique 1.0. Los cambios detallados, incluidas las funciones opcionales de
servidor y consola ya entregadas, están en el [CHANGELOG](../../CHANGELOG.md).
Las entradas anteriores siguen siendo registros históricos; el build `meada 0.1.0` es el del
primer recibo de aceptación, abajo.

## Distribución y comunidad

La [ADR 0010](../adr/0010-distribution-and-community-practice.md), el
[trunk #17](https://github.com/ClaudioMascaro/meada/pull/17) y la [configuración npm #258](https://github.com/ClaudioMascaro/meada/pull/258) sustentan los
canales: Cargo, binarios para seis destinos Linux/macOS/Windows (x86_64 y arm64), instalador shell
para Linux/macOS, npm, además de imágenes OCI default/cloud y el archivo de la consola. Vea la
[configuración de distribución](../../dist-workspace.toml), el
[workflow de release](../../.github/workflows/release.yml), el
[workflow de contenedor](../../.github/workflows/container.yml) y el
[test de imagen](../../scripts/container-smoke).

**La configuración no demuestra la publicación.** La publicación npm y las comprobaciones de una
instalación real siguen a cargo del mantenedor. `npx @meada/meada --version` y `npx @meada/meada mcp` contra una
fixture pública deben verificarse después de publicar. El workflow preparado deja la release de
GitHub como borrador; la publicación humana dispara la distribución OCI. Para regenerar y comprobar
el workflow completo con esta política, ejecute `python3 scripts/release-workflow --write` y
`python3 scripts/release-workflow --check` en la raíz, con cargo-dist **0.32.0** en PATH.

El workflow de release solo prepara (stage) el paquete npm: el
[workflow de staging](../../.github/workflows/publish-npm-staged.yml) ejecuta `npm stage publish`, y
el secreto `NPM_TOKEN` no puede hacer pública una versión. El paquete solo está disponible en npm
después de que el mantenedor apruebe la versión preparada con 2FA (`npm stage list meada`, luego
`npm stage approve <id>`). El cuerpo de la release de GitHub que escribe cargo-dist ya muestra
`npm install meada@<version>`, por eso el mantenedor aprueba el stage antes de publicar el borrador.
El primer stage también crea un placeholder público `0.0.0-stage`, que no es una release.

La práctica de comunidad del trunk tiene [CONTRIBUTING](../../CONTRIBUTING.es.md),
[Código de Conducta](../../CODE_OF_CONDUCT.es.md) (Contributor Covenant 3.0) y
[SECURITY](../../SECURITY.es.md), todos en pt-BR, inglés y español; tres
[formularios de issue](../../.github/ISSUE_TEMPLATE) y un
[template de PR](../../.github/pull_request_template.md), cada uno trilingüe.
Los contactos de moderación/reporte aún tienen campos que debe completar el mantenedor.
La administración de checks obligatorios, el reporte privado de vulnerabilidades y las etiquetas
para contribuyentes requieren una comprobación separada. La existencia de archivos no demuestra
esas configuraciones. Los mensajes CLI en español siguen fuera de R1, en la
[issue #103](https://github.com/ClaudioMascaro/meada/issues/103).

## Mediciones públicas de aceptación

Las fuentes de estas medidas son dos recibos públicos en #152. El [recibo del 24/10/2026](https://github.com/ClaudioMascaro/meada/issues/152#issuecomment-6379316350)
conserva dos ejecuciones completas y registra: AMD Ryzen 7 5825U, 16 CPU lógicas, 7,16 GiB de RAM,
Ubuntu 24.04.5 LTS, x86_64. El build medido era
`9b99c3a4091b6c1b2c590c43059763f25b6987ef`, `meada 0.1.0`; no son mediciones de cada head
posterior de documentación.

| Métrica | Objetivo | Primera ejecución completa | Reejecución completa |
| --- | --- | --- | --- |
| Indexación en frío del workspace configurado | <= 7 s | 12,680 s, no alcanzado | 2,711 s, alcanzado |
| Tamaño del índice raíz | <= 37 MB | 21,057536 MB, alcanzado | 21,057536 MB, alcanzado |
| Reindexación de un archivo en el workspace | <= 1 s | 1,346 s, no alcanzado | 1,152 s, no alcanzado |
| Resultado compacto MCP `tools/list` | <= 1.000 tokens | 622, alcanzado | 622, alcanzado |
| Mayor respuesta predeterminada entre 11 consultas | <= 2.000 tokens | 1.996, alcanzado | 1.996, alcanzado |

MB significa 10^6 bytes; la estimación es ceil(bytes UTF-8 / 4). Las fixtures públicas complementan
el workload privado en el recibo; este no afirma que cada función ocurra naturalmente en la raíz
privada. Se mantienen ambos conjuntos de números, sin seleccionar solo la ejecución mejor.

El [recibo del 30/10/2026](https://github.com/ClaudioMascaro/meada/issues/152#issuecomment-6531862493) reejecuta la aceptación
en la misma máquina con el build de release del main `1d648ad6` (después de #391). La configuración
original del 24/10 no se conservó, así que el workspace fue reconstruido y sus números absolutos
no se comparan directamente con el recibo anterior; cada ejecución es la mediana de tres muestras,
y la tabla muestra la ejecución más silenciosa y el rango de las cuatro.

| Métrica | Objetivo | Ejecución más silenciosa | Cuatro ejecuciones |
| --- | --- | --- | --- |
| Indexación en frío del workspace configurado | <= 7 s | 5,586 s, alcanzado | 5,586 a 6,625 s, alcanzado en todas |
| Tamaño del índice raíz | <= 37 MB | 31,883266 MB, alcanzado | idéntico en todas |
| Reindexación de un archivo en el workspace | <= 1 s | 0,931 s, alcanzado | 0,931 a 1,123 s, alcanzado en 2 de 4 |
| Resultado compacto MCP `tools/list` | <= 1.000 tokens | 643, alcanzado | idéntico en todas |
| Mayor respuesta predeterminada entre 11 consultas | <= 2.000 tokens | 1.999, alcanzado | idéntico en todas |

La reejecución del 30/10/2026 alcanza cuatro de los cinco objetivos: indexación en frío (medianas
de 5,586 a 6,625 s, <= 7 s), tamaño del índice raíz (31,883266 MB, <= 37 MB), `tools/list`
(643 tokens, <= 1.000) y mayor respuesta predeterminada (1.999 tokens, <= 2.000). La reindexación
de un archivo (<= 1 s) alcanzó el objetivo en las dos ejecuciones más silenciosas (0,99 s y
0,931 s) y lo perdió en las dos con carga media cercana a 3 (1,068 s y 1,123 s). El mantenedor
[dispensó el objetivo de reindexación para 1.0.0](https://github.com/ClaudioMascaro/meada/issues/350#issuecomment-6532716065), registrado en [#350](https://github.com/ClaudioMascaro/meada/issues/350).

### Límites conocidos

La reindexación de un archivo queda cerca de 1 s y lo excede bajo carga. #350 sigue abierta para
1.x, con la meta de 1 s con holgura bajo carga común; una aceleración no cambia ninguna salida,
así que sale como patch o minor.

El [benchmark público en CI](../../tests/it/benchmark.rs) conserva JSON/Markdown y una tabla en el
resumen del job. Sus tiempos son informativos y no sustituyen esta aceptación privada.
Los tests existentes siguen imponiendo los presupuestos determinísticos de tokens.

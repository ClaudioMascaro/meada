### F1: the forms of `uses`

- **Expected counts, not rates.** `uses` holds no expression, so every call can be counted from the source. Before the run, the answer key writes per form of `uses`: the links expected, the unresolved consumers per cause, the external calls (no side) and the absent marks. The report must match it.
- **Seed.** The maintainer counted the pinned corpus from the code at its pinned commits, without running Meada. It is a seed to check the answer key against, not the answer key: 400 `uses`, none with an expression; 184 calls inside the workspace (104 by full name, 5 local pipelines, 75 `./<folder>`); 4 of them cross repositories, all of them pipelines; 167 are in `slsa-framework/slsa-github-generator`.
- **Open misses, per cause.** Each cause is an entry the maintainer approves with its expected count. By ADR 0028's own rule about 34 of the 75 `./<folder>` calls stay unresolved (in a reusable pipeline, in a composite action, in a job with no checkout of its own repository at the default path): 18% of the 184, which no rate chosen blind would allow. A cause off the list counts 0, and a count above the expected one is a finding.
- **The corpus grows.** 4 links across repositories are under the floor of 30, so the links across repositories are unmeasured today. The corpus grows to at least 30 of them by a rule written here before the search and run by someone who does not implement A9. The rule: no provider file answers for more than a third of the 30; calls of an action across repositories are included (there are none today: the 4 are pipelines); a consumer whose pinned commit has a public workflow run is preferred. The result is pinned in the infrastructure corpus list of `prove-meada`, with URL, commit and licence.
- **Answer key from execution.** GitHub's "Get a workflow run" response lists `referenced_workflows` (path, sha and ref of each reusable pipeline the run used). It is captured once for the pinned commits, stored with the corpus, and read one way only: a pipeline it shows that Meada did not link is a missed call, and its silence proves no link wrong. It covers pipeline files, not actions. Two GitHub facts are confirmed before it is used, each with its source: whether it includes nested calls, and whether it includes the calls of skipped jobs.
- **Elsewhere, a judge.** Where no run exists, a fresh agent judges each link against the source. It lists the `uses` from the code before it opens the export. The maintainer samples its marks, the "correct" ones included, before the report counts.
- **Orphan lines.** F1 prints an orphan line for a reusable pipeline or an action nothing calls (#827). That pair is in the gate (#N1) and is judged here, with the links of F1 and on the same corpus. The source counts these too: before the run, the answer key lists the providers of the workspace that no `uses` of the workspace names, in a scope that holds at least one provider and one consumer of the kind. The report must match the list. A line for a provider the source shows a call to is a false line, counted per cause, and each cause is an entry the maintainer approves with its expected count. One cause is named now, and its count is written from the source before the run: a provider whose only calls are among those ADR 0028's rule leaves unresolved (the `./<folder>` calls above). A false line by a cause off the list counts 0. A provider of the list with no line is a silent absence. With fewer than 30 judged lines the pair is unmeasured, and the corpus that grows for the links across repositories is chosen to hold unused providers too.

### F2: the `run` script

- Unmeasured until a corpus exercises it: the pinned corpus holds no install by name, no `uvx`, no `pipx run`, no `docker push` and no Python package. #854 looks for one. If it finds a set, this ticket pins it and judges it as F1 is judged: each install read from a `run` script, each program link with its level, each image builder side on a CI step and the image link it gives.
- On such a corpus the provider is the true publisher of the package, so a link by name is right by construction. What this part approves is the reading of the `run` script by the command table. Inference by name is bounded elsewhere: by the `inferred` level and the fork probe (#850), and by the count of installs by name in the private aggregates.
- The report counts the installs whose name equals a provider of the workspace, even when the count is zero.
- F2 ships after #850, so that no install by name alone is `exact`.
- Cost, accepted: F2 stays longer on its branch than F1, and it carries its own schema rise with a rebuild of the indexes.

### F3: declared permissions

- Unmeasured today: on the pinned corpus 20 links compare permissions, and none carries `permissions mismatch` or `not declared`, so there is no positive case. The repositories that grow the corpus of F1 are chosen to feed F3 as well. F3 ships when a report judges positive cases past the floor.

### For every slice

- **Thresholds.** The defaults of ADR 0029: no wrong `exact` link, no silent absence, no `ambiguous` link whose candidates lack the right provider, at most 1 wrong `inferred` link in 10 (valid from 30 judged).
- **Floor.** A level, a form of `uses`, a row of the command table or the links across repositories with fewer than 30 judged statements is unmeasured, not approved. The report counts statements per form and per row.
- **Ceilings.** A new ceiling is the maintainer's decision, one per entry. It is never the automatic exit of a failed criterion.
- **The private half.** In the counts of #837, the maintainer adds, as aggregates only: how many calls the execution record shows against how many links Meada found, and how many installs by name alone the workspace holds.
